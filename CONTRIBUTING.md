# Как вносить изменения

Короткие правила для всех, кто пишет код в этот репозиторий.
В `main` напрямую не пушим — всё идёт через **issue → ветка → Pull Request**.

## 1. Задача (issue)

- Любая работа начинается с issue. Нет issue — создай (или попроси создать).
- Возьми задачу: назначь себя в поле **Assignees**, чтобы двое не делали одно и то же.
- Непонятно, что делать — спроси в комментариях к issue, а не в личке:
  ответ пригодится следующему.

## 2. Ветка

Ветку создаём от свежего `main`:

```bash
git checkout main
git pull
git checkout -b fe/4-save-toast
```

Имя ветки: `<область>/<номер-issue>-кратко-латиницей`.
Область: `fe` — фронтенд, `be` — бэкенд, `fs` — и то и другое, `docs` — документация.

## 3. Коммиты

- Небольшие и по делу; сообщение понятно без чтения кода:
  `Добавить toast при сохранении точки`, а не `fix` или `правки`.
- Не коммитим `.env`, ключи, пароли, `node_modules/`, `dist/`.
- Перед коммитом посмотри, что именно уходит: `git status` и `git diff`.

## 4. Перед Pull Request

```bash
npm run typecheck   # типы
npm run build       # сборка
```

Оба должны пройти без ошибок. Затем проверь изменение руками в `npm run dev`.

Если `main` успел уйти вперёд — подтяни его в свою ветку:

```bash
git pull origin main
```

## 5. Pull Request

```bash
git push -u origin fe/4-save-toast
```

GitHub покажет ссылку на создание PR (или кнопку **Compare & pull request**).

- **Куда:** в `main`.
- **Название:** как у issue или короче, по-русски.
- **Описание:** заполни шаблон, который подставится сам. Обязательно строка
  `Closes #4` — тогда issue закроется автоматически после мержа.
- Для изменений интерфейса — скриншот (с телефона, если правка про мобильный вид).
- Один PR — одна задача. Не смешивай разные issue в одном PR.

## 6. Ревью и мерж

- Нужен **1 апрув** и зелёная проверка **CI** (сборка).
- Замечания ревьюера правь новыми коммитами в ту же ветку — PR обновится сам.
- Мержит автор PR после апрува, кнопкой **Squash and merge**.
- После мержа удали ветку (кнопка **Delete branch**).
